# Лаб 3: Чанарын сценарио -> SLO -> k6 threshold (F.CSA313)

**Оюутан:** А.Ууганбаяр (B242270014)

Өөрийн локал API-д зориулж performance, reliability, availability сценарио бичиж, SLO болгон томьёолж, k6 threshold-оор автоматаар шалгуулна.

## Ёс зүй
Бүх load тестийг зөвхөн өөрийн компьютер дээрх локал сервер (`http://localhost:3000`) рүү хийсэн.

## Файлууд
| Файл | Зорилго |
|---|---|
| `server.js` | Тестлэх локал API (`/cart/add`, `/report`, `/pay`) |
| `slo-test.js` | SLO-г k6 threshold болгон кодчилсон тест |
| `slo-test-fail.js` | Threshold-ыг зориуд эвдсэн (FAIL) хувилбар |
| `scripts/run-fail.sh` | FAIL хувилбарыг ажиллуулж exit code-ыг тэмдэглэнэ |
| `scripts/chaos.sh` | 10 секундын зогсолттой chaos туршилт |
| `results/` | k6-ийн бүтэн текст гаралтууд |
| `screenshots/` | Дэлгэцийн зургууд |

## Ажиллуулах
```bash
npm install
node server.js                                  # нэг terminal дээр

k6 run slo-test.js 2>&1 | tee results/pass.txt  # PASS
bash scripts/chaos.sh                           # chaos (server.js-ийг зогсоосон байх)
bash scripts/run-fail.sh                        # FAIL + exit code
```

## k6 хувилбар
```
k6 v2.4.0 (commit/devel, go1.27.4, darwin/arm64)
```

| Гадаад өдөөлт | Хэрэглэгч `POST /cart/add` хүсэлт илгээнэ. |

| Хэмжүүр | Хариуны хугацааны p95 < 10 мс (1 минутын цонх, 20 VU). |

| Хэмжүүр | Availability = амжилттай хүсэлт / нийт хүсэлт > 90% (2 минутын цонх). Сэргэх хугацаа: нийт зогсолт <= 15 секунд (`results/chaos-timeline.txt`). |

## Алхам 3: SLO
| Сценарио | SLI | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | `/cart/add` latency | p95 < 10 мс | 20 VU тогтмол ачаалал, 1 мин |
| Reliability | `/pay` error rate | < 8% | 1 мин, 20 VU |
| Availability | бүх хүсэлтийн амжилтын хувь (`checks`) | > 90% | 2 мин, 10 секундын зогсолттой |
| `/report` (нэмэлт) | `/report` latency | p95 < 450 мс | 20 VU, 1 мин |

Эдгээр босго `slo-test.js` доторх threshold-той ИЖИЛ байна (`p(95)<10`, `rate<0.08`, `rate>0.90`, `p(95)<450`).

**Босго сонгосон үндэслэл:**
- **Performance (10 мс):** localhost дээр хэмжсэн p95 нь 1.45 мс (`results/pass.txt`). Анхны жишээ босго 200 мс нь үүнээс ~140 дахин сул, юу ч хэмжихгүй тул хэмжсэн утгын ~7 дахин нөөцтэй 10 мс-ийг сонгосон. Энэ нь хэлбэлзлийг багтааж, харин хэд дахин удаашрах регрессийг барина.
- **Reliability (8%):** серверт 5% алдаа суулгасан, хэмжилтүүд 3.77%-5.36% гарсан. Ойролцоогоор 930 дээжинд стандарт хазайлт ~0.7% тул 8% нь санамсаргүй хэлбэлзлээр унахгүй, харин алдааны хувь хоёр дахин өсвөл барьдаг бодитой босго.
- **Availability (90%):** хэвийн үед `checks` ~98% (зөвхөн `/pay`-ийн 5% алдаа орно), тиймээс 90% нь хэвийн ажиллагааг хүндрүүлэхгүй бөгөөд 10% буюу бодитой зогсолтыг барина.
- **`/report` (450 мс):** сервер хамгийн ихдээ ~400 мс хүлээдэг, хэмжсэн p95 ~391 мс тул ~15%-ийн нөөцтэй.

**Error budget (availability 90%, 2 минутын цонх):**
- Цагаар: 120 с x 10% = **12 секунд**. 10 секундын зогсолт үүнд багтана.
- Хүсэлтээр: chaos тестэд 5691 хүсэлт, 5691 x 10% = **~569 алдаатай хүсэлт** зөвшөөрөгдөх ёстой.

## Алхам 5: Chaos туршилт
`bash scripts/chaos.sh`: 2 минутын тестийн ~40-р секундад сервер зогсоож, 10 секундын дараа дахин асаасан. Цагийн бичлэг (`results/chaos-timeline.txt`):

```
[21:40:22] k6 эхэллээ (2 минут)
[21:41:02] сервер ЗОГСООНО
[21:41:12] сервер ДАХИН АСААЛАА (10 секундын зогсолт)
[21:42:24] k6 дууслаа, exit=99
```

Үр дүн (`results/chaos.txt`):

| Threshold | Хэмжсэн | Үр дүн |
|---|---|---|
| `checks` rate>0.90 | 87.82% | **FAIL** |
| `http_req_failed{name:pay}` rate<0.08 | 15.34% | **FAIL** |
| `http_req_duration{name:cart}` p(95)<10 | 1.16 мс | PASS |
| `http_req_duration{name:report}` p(95)<450 | 387.97 мс | PASS |

**Бодит availability (хүсэлтээр):** нийт 5691 хүсэлт, 693 нь амжилтгүй. Availability = 4998 / 5691 = **87.82%**. Зогсолтод ~201 iteration (20 VU x ~10 с) x 3 хүсэлт = 603 хүсэлт унасан, үлдсэн 90 нь `/pay`-ийн ердийн ~5% алдаа.

**Error budget хэтэрсэн үү:** Цагаар тооцвол 10 с зогсолт 12 с budget-д багтдаг (110/120 = 91.7%). Харин хүсэлтээр тооцвол зөвхөн зогсолтын 603 алдаа ч 569-ийн budget-ээс их тул budget **хэтэрсэн**.

**Яагаад хоёр тоо зөрж байна:** k6-ийн `checks` нь цагийн биш ХҮСЭЛТИЙН хувь. Сервер унасан үед хүсэлт `connection refused`-аар агшин зуур буцдаг тул iteration ~1.0 с (хурдан алдаа + 1 с sleep) бол хэвийн үед ~1.3 с (`/report`-ын 200-400 мс хүлээлттэй). Иймээс зогсолтын нэг секунд хэвийн секундээс олон хүсэлт "иддэг": 10 секунд нь тестийн цагийн 8.3% боловч бүх хүсэлтийн 603/5691 = 10.6%-ийг эзэлсэн. Тэгэхээр SLO 90% нь хэт өөдрөг биш, харин цагаар тооцсон 12 секундын budget хүсэлтээр тооцохоос илүү өгөөмөр байсан.

**Reliability threshold мөн FAIL болсон уу:** Тийм (15.34%). Сервер унахад `/pay`-ийн хүсэлт бүр унадаг тул нэг эвдрэл availability ба reliability хоёр SLO-г зэрэг зөрчсөн. Үүнийг тусгаарлахын тулд reliability-ийн SLI-д зөвхөн сервер хариулсан (HTTP статустай) хүсэлтийн алдааг тоолж, холболтын алдааг (status 0) зөвхөн availability-д тоолох custom metric ашиглаж болно.

## Алхам 6: Threshold-ыг зориуд эвдэх
`slo-test-fail.js` нь `/report`-ын threshold-ыг `p(95)<100` болгосон, бусад нь ижил. `bash scripts/run-fail.sh` (`results/fail.txt`):

- FAIL мөр: `✗ 'p(95)<100' p(95)=391.49ms` (`http_req_duration{name:report}`)
- k6-ийн exit code: **`exit=99`** (threshold зөрчигдсөн). CI pipeline яг энэ exit code-оор build-ийг зогсоодог.
- Бусад threshold-ууд `✓` (checks 98.21%, cart 1.44 мс, pay 5.36%).
- Сервер ямар ч үед 200 мс-ээс хурдан хариулдаггүй тул энэ нь найдвартай FAIL. Харин `/cart/add`-ыг `p(95)<50` болговол localhost дээр PASS хэвээр үлдэнэ, учир нь хэмжсэн p95 1.44 мс нь 50 мс-ээс хол доогуур (сүлжээний хоцролтгүй, handler нь хоосон).

## Дүгнэлт
Сценарио -> SLO -> threshold шилжилтэд хамгийн хэцүү нь "сул босго"-оос зайлсхийх байсан: анхны 200 мс босго хэмжсэн 1.45 мс-ээс ~140 дахин сул байсан тул бодит хэмжилтэд үндэслэж 10 мс болгосон. Мөн анхны хэмжилт 3000 порт дээр өмнөх лабын сервер ажиллаж байснаас болж буруу гарсныг (`/report` 1 мс, `/pay` 0% алдаа) гараар `curl`-ээр шалгаж олсон нь хэмжилтийг баталгаажуулах нь босго тохируулахаас өмнө чухал гэдгийг харуулсан. Reliability-ийн 8%-ийг серверт суулгасан 5% болон хэмжсэн 3.77-5.36%-ийн хэлбэлзэлд үндэслэсэн. Chaos туршилт availability сценариогийн хэмжүүрийг хэсэгчлэн үгүйсгэсэн: цагаар тооцоход 10 секундын зогсолт 12 секундын budget-д багтдаг ч хүсэлтээр тооцоход availability 87.82% буюу 90%-иас доош гарсан. Шалтгаан нь зогсолтын үед хүсэлт шууд алдаатай буцдаг тул нэг секунд хэвийн секундээс олон хүсэлт иддэг (10 секунд нь цагийн 8.3% боловч хүсэлтийн 10.6%). Иймээс availability SLO-г хүсэлтээр, эсвэл хоёр аргаар хоёуланг нь тодорхойлох нь зөв. Нэг эвдрэл availability (87.82%) ба reliability (15.34%) хоёр SLO-г зэрэг зөрчсөн тул тэдгээрийн SLI-г тусгаарлахын тулд reliability-д зөвхөн серверийн хариулсан хүсэлтийг тоолох нь зүйтэй. Latency threshold-ууд (cart 1.16 мс, report 387.97 мс) зогсолтын үед ч PASS хэвээр байсан нь latency нь зөвхөн амжилттай хариунаас хэмжигддэг тул availability SLO-г орлохгүйг харуулсан. FAIL туршилтаар `/report`-ын `p(95)<100` босго 391.49 мс-ээр зөрчигдөж k6 `exit=99` буцаасан нь CI pipeline-ийн quality gate зарчим юм. Хязгаарлалт: бүх туршилт нэг машин дээр localhost рүү, түвшин тус бүр нэг л удаа хийгдсэн тул үр дүн машин, цагаас хамаарна. Нэг эвдрэл хэд хэдэн SLO-д нөлөөлдөг тул сценариуд бие даасан биш, SLO-г хослуулан тавих хэрэгтэй гэж дүгнэв.

## AI ашигласан тухай
Төслийн эхлэл файлууд, сценарио болон README-ийн ноорогийг Claude-ийн тусламжтайгаар бэлдсэн, хэмжилт бүрийг өөрийн компьютер дээр өөрөө ажиллуулж баталгаажуулсан. Эхний хувилбарт зааврын жишээ `p(95)<200` босго байсан нь localhost дээр хэмжсэн 1.45 мс-тэй харьцуулахад хэт сул байсан тул 10 мс болгож зассан. AI-д k6 болон интернэт байхгүй тул тестийг өөрөө ажиллуулж чадаагүй, бүх тоо миний хэмжилтээс гарсан. Chaos туршилтыг зааврын гараар Ctrl+C хийх аргын оронд `scripts/chaos.sh` скриптээр хийсэн (зогсолтын цаг `results/chaos-timeline.txt`-д бий), ингэснээр зогсолт тогтмол 10 секунд болсон.
